## 一、项目介绍

### 1.1 一句话介绍

**基于自训 YOLOv8s 人头检测模型的智能自习室监测系统**——边缘端实时统计每间教室的人数、空座与在座时长，监测摄像头异常，并用本地大模型提供自然语言数据问答（Text2SQL），形成"监测 → 展示 → 分析 → 推荐"的完整闭环。

### 1.2 背景与痛点

| 痛点 | 本系统的解法 |
|---|---|
| 自习室/图书馆高峰期"找座难"，学生逐间跑 | 大屏/门户实时查看每间教室空座，AI 推荐最优选择 |
| 俯拍视角下学生只见头顶后脑，**人脸检测完全失效** | 改用人头检测（CrowdHuman 数据集自训模型，mAP50=0.842） |
| 管理员不知道哪间教室利用率低、什么时段最挤 | 7天×24h 占用率热力图 + 黄金/高峰时段分析 |
| 视频回传服务器带宽大、隐私风险高 | **边缘计算**：检测在教室本机跑，只传数字不传画面 |
| 通用大模型问答对私有数据无能为力 | 本地 Ollama + Text2SQL，数据不出内网 |

### 1.3 用户与角色

| 角色 | 能力 |
|---|---|
| **访客** | 登录页查看全馆实时统计（教室数/座位数/当前空座） |
| **普通用户** | 占用总览、教室收藏、教室详情（座位示意+24h趋势）、历史规律（热力图/黄金时段）、空座提醒、AI 问答 |
| **管理员** | 普通用户全部能力 + 教室管理（增删改/级联清数据）、用户管理（新增/升降权/重置密码/删除） |
| **运营大屏** | 挂墙展示：全局 KPI、实时人流曲线、占用率仪表盘、排行、分时热度 |

### 1.4 核心指标

| 指标 | 数值 |
|---|---|
| 人头检测 mAP50 | **0.842**（CrowdHuman val，4370 图 / 97,285 头框） |
| 单帧推理耗时 | 11.9ms @960 / 152ms @1280（RTX 5070 Laptop，DirectML） |
| 端到端数据延迟 | ≤ 5 秒（上报周期 + 前端轮询） |
| AI 问答 SQL 成功率 | 一次 ~70% → 自愈重试后 ~95% |
| AI 热响应 | ~1.7 秒（qwen2.5:1.5b） |
| 部署方式 | `docker compose up` 一键拉起 4 容器 |

## 二、训练模型数据来源

### 2.1 数据集：CrowdHuman（旷视开源）

| 项 | 值 |
|---|---|
| 规模 | 15,000 训练图 + 4,370 验证图 |
| 场景 | 街景/校园远景人群，多为**俯拍/远距** |
| 标注 | 全身框(fbox) + 头框(hbox) + 可见框(vbox) |
| 头框数量 | 训练集 331,991 个，平均每图 22 个 |
| 关键特性 | 包含**背对镜头**的人——正是俯拍自习室的核心场景 |

**为什么不用人脸数据集（WIDER FACE 等）**：项目早期先训过人脸模型（mAP50=0.99，非常好），但真实自习室顶置摄像头俯拍下学生只有头顶和后脑勺，人脸检测直接失效。这是本项目立项的出发点：**换检测目标（头），而不是换模型**。

### 2.2 数据转换与清洗（convert_crowdhuman.py）

CrowdHuman 原始 odgt 格式（每行一个 JSON）转 YOLO txt 格式（`class cx cy w h` 归一化）。转换不是简单换坐标，关键在**按官方规则过滤脏标注**：

| 过滤项 | 数量(train) | 原因 |
|---|---|---|
| mask 区域内的框 | 85,809 | 被遮挡超阈值，头框质量差 |
| ignore 标记的框 | 20,178 | 官方明确忽略（画面边缘裁切等） |
| 无效框（宽高≤0） | 814 | 坐标越界 |

**质量校验**（抽样 500 图 / 11,420 个头框）：
- 头框中心落在对应全身框内：99.9%
- 头框位于全身框上 40% 区域：96.5%
- 头框平均宽高比 0.86（接近方形，符合头部形状）
- 头宽/全身宽 ≈ 0.38（符合人体比例）

### 2.3 训练配方（WSL + RTX 5070 Laptop 8GB）

```bash
yolo detect train model=yolov8s.pt data=crowdhuman/data.yaml \
  imgsz=768 batch=8 epochs=100 \
  optimizer=SGD lr0=0.01 cos_lr=True patience=30 workers=4
```

- **SGD 而非 AdamW**：实测 AdamW + lr0=0.01 在此任务损失振荡不收敛（真实踩坑），SGD 稳定
- **imgsz=768 / batch=8**：8GB 显存上限（960 会 OOM）
- **patience=30**：第 81 epoch 早停
- 训练档结果：val mAP50 = 0.789

### 2.4 关键技巧：训练 768、推理 1280

训练与推理分辨率可以不一致——小目标在高分辨率下更清楚。同一权重导出多版 ONNX：

| 推理分辨率 | mAP50 | mAP50-95 | 单帧耗时 |
|---|---|---|---|
| 768（训练档） | 0.789 | 0.494 | 2.3ms |
| 960 | 0.819 | 0.524 | 11.9ms |
| **1280（部署用）** | **0.842** | **0.546** | 152.5ms |

**零额外训练成本，mAP50 +5.3 个点**。自习室帧率要求不高，选 1280 版精度优先。

### 2.5 分级置信度阈值

统一阈值的矛盾：远景小头置信度天然低（~0.2），近处大头高（~0.8）。阈值高则漏小头，低则大框误检泛滥。解法：

```python
# 小框（宽<32px）用低阈值 0.15，大框用高阈值 0.35
threshold = np.where(pred_w * ratio < 32, 0.15, 0.35)
```

## 三、技术栈

| 层 | 技术 | 选型理由 |
|---|---|---|
| 检测模型 | YOLOv8s → ONNX | 单类检测够用；s 版精度/速度平衡 |
| 推理引擎 | onnxruntime-directml | Windows 免装 CUDA 全家桶，DirectML 走 GPU |
| 目标跟踪 | 纯 NumPy 自研 IOU 跟踪器 | 场景静态（坐着为主），ByteTrack 属过度设计 |
| 后端 | FastAPI + PyMySQL | 异步、自动 Swagger、轻量 |
| 认证 | PBKDF2 + HMAC 签名 Token | 无 JWT 依赖、无状态、7 天有效 |
| 数据库 | MySQL 8.0 | 时序快照 + 会话 + 用户，关系型足够 |
| 大屏 | 单文件 HTML + ECharts | 零构建、挂任意屏幕 |
| 管理门户 | Jinja2 SSR 多页应用（FastAPI 同源渲染） | 服务端权限判定 + HttpOnly Cookie + CSRF；替代了 Streamlit 与前端 SPA |
| LLM | Ollama + qwen2.5:1.5b（可切 7b） | 本地运行数据不出内网；1.5b 热响应 1.7s |
| 部署 | Docker Compose（3 容器） | api（含门户 SSR）/ mysql / ollama 一键拉起 |

## 四、功能具体实现方法

### 4.1 人头检测（head_detector.py）

每帧流水线：

```
原图 (1920×1080)
 → letterbox 等比缩放 1280×1280（短边补灰, 不变形）
 → BGR→RGB / 归一化 / HWC→CHW / 加 batch 维
 → ONNX 推理（输出 8400×5: cx,cy,w,h,score）
 → 分级阈值过滤（见 2.5）
 → NMS（IoU>0.45 只留最高分）
 → 坐标映射回原图
 → 输出 [([x1,y1,x2,y2], score), ...]
```

letterbox 而非直接 resize：拉伸会把头压扁变形，与训练分布不符。

### 4.2 多目标跟踪（tracker.py）

解决"逐帧数人头会抖动"（同一个人这帧检到下帧漏了）。每帧 `update(检测框)`：

1. **预测**：轨迹按上帧速度匀速外推
2. **匹配**：检测框 vs 轨迹算 IoU 矩阵，>0.25 贪心配对；IoU 不够但质心近的兜底
3. **确认**：连续命中 ≥3 帧（min_hits）才计入人数——单帧误检（椅背/海报）活不过 3 帧
4. **老化**：连续失配 >12 帧（max_age）判定离场——低头/遮挡导致短暂漏检不会误判离开
5. **归档**：离场轨迹 → 会话记录（track_id, 起止时间, 时长）

产出：当前人数 = 确认轨迹数；人均在座时长 = 会话聚合。参数均在实际自习视频上调优。

### 4.3 摄像头异常守卫（camera_guard.py）

**零额外模型**，三信号判定：

| 异常 | 判定信号 | 确认条件 |
|---|---|---|
| 遮挡 | 亮度骤降 + 拉普拉斯方差（纹理）趋零 + 检测人数为 0，三者同时 | 连续 8 帧 |
| 移动 | 相邻帧差分变化像素占比超阈值 | 连续 4 帧 |

防抖：自动发恢复通知；60 秒告警冷却。夜晚教室暗但纹理仍在——三条件与避免误报。

### 4.4 边缘上报（edge_agent.py）

教室电脑常驻进程：取流 → 检测 → 跟踪 → 守卫 → 每 interval 秒 `POST /api/report`（只传数字，几十字节）。视频播完/Ctrl+C 时 `flush_remaining_sessions()` 把在场的人也归档，数据不丢。

### 4.5 用户认证（server.py）

- **口令**：PBKDF2-HMAC-SHA256（150k 迭代 + 16 字节盐）哈希入库
- **Token**：`HMAC(用户名|过期时间, 服务器密钥)` 签名，无状态验证（不查库），7 天有效
- **种子管理员**：首次启动自动建 users 表 + 创建 admin
- **管理接口**：角色校验（403），自我保护（不能删自己/改自己角色）

### 4.6 可视化大屏（web/index.html，:8000/ui）

- 6 张 KPI 卡（数字滚动动画、涨跌角标、sparkline）
- 全局实时人流曲线（5s 流式追加、末端涟漪点、均值线）
- 总占用率仪表盘（渐变进度环）、教室占用排行（实时重排赛跑动画）
- 分时热度柱状图（每小时聚合 + 峰值虚线）
- 座位点阵（按占用数从左至右填充，绿=占/蓝=空，弹跳动画）
- AI 问答抽屉、告警条、粒子背景 + 鼠标交互（粒子避让/连线、卡片 3D 倾斜、点击涟漪）

### 4.7 管理门户（templates/portal/，:8000，Jinja2 SSR 多页应用）

由 FastAPI 同源渲染 6 个页面（登录/总览/历史规律/AI/教室管理/用户管理），与 API 同端口部署。会话存 **HttpOnly Cookie**（XSS 偷不走），写操作校验 `X-Requested-With` 头（CSRF 防护），页面权限服务端判定；登录连续失败 5 次锁定 15 分钟。

- **登录页**：左右分栏——左侧品牌区（Logo + 特性卡 + **未登录可见的实时统计**），右侧登录/注册滑块切换 Tab
- **占用总览**：教室卡片（进度条流光 + 3D 倾斜 + 涟漪）、搜索 + 状态筛选、收藏（localStorage 持久化）
- **教室详情弹窗**：座位示意点阵（悬停放大辉光 + 跟随提示）+ 24h 趋势双曲线 + 均值线
- **历史规律**：见 4.8
- **管理员**：教室 CRUD（可选级联删历史数据）、用户管理（新增/升降权/重置密码/删除）

### 4.8 历史规律分析（"什么时候去自习"决策）

后端 `/api/trends`（SQL 聚合）：

- 单教室：`AVG(occupied_count / total_seats)` 按 天×小时 分组
- 全馆：每个采样时刻 `SUM(occupied)/SUM(seats)` 再按时段平均
- **黄金时段**：按"星期×小时"聚合历史占用率，取空座率最高 Top3（如"周一 16:00–17:00 空座率 88%"）；反向输出高峰"避开"时段

前端：ECharts 热力图（7天×24h 格矩阵，深蓝→红渐变，悬停数值）+ 近 7 天日均值柱状图（渐变柱+均值虚线）+ 教室筛选（全馆/单教室）。

### 4.9 空座提醒（浏览器通知）

- 用户授权 Notification 后，前端每 15 秒检查**收藏的教室**
- 空座从 "<3" 翻转为 "≥3" 时弹系统通知（含空出数量）
- 5 分钟冷却防轰炸；纯前端实现，零后端改造

### 4.10 AI 问答（Text2SQL + 本地 Ollama）

选 **Text2SQL 而非 RAG**：数据是结构化时序数字，SQL 精确（"15点平均29.2人"），语义检索只能给模糊相似结果。

五步链路：

```
中文问题 + Schema提示词(含正确SQL示例, 明确"rooms表无人数列")
 → Ollama qwen2.5 生成 SQL
 → 安全校验: 只放行 SELECT/WITH; 黑名单拦截写操作; 剥离 markdown 围栏
 → 执行(包装子查询强制 LIMIT 50)
 → 报错则把 MySQL 错误回喂模型重新生成(自愈重试, 最多2次)
 → 查询结果+原问题 → 大模型组织中文回答(时长自动换算)
```

模型选择：qwen2.5:1.5b 热响应 ~1.7s（7b 需几十秒）；小模型 SQL 幻觉问题靠**强化 schema 提示 + 自愈重试**工程手段弥补。实测："删掉 records 表"被安全校验拦截。

## 五、功能实现流程

### 5.1 端到端数据流（一次完整旅程）

```
教室摄像头
 → edge_agent: 检测(8个头) + 跟踪(8条轨迹) + 守卫
 → 新人入画, 连续3帧确认, ID=7, 人数8→9
 → 30秒到: POST /api/report {camera_id, head_count:9}
 → MySQL records 落库(occupied 封顶 min(9, 45) ≤ 座位数)
 → 大屏5秒内轮询到: 卡片闪橙光"▲+1", 曲线末端跳到9
 → 2小时后离开: 12帧未匹配 → 会话归档{track_id:7, 14:00→16:00}
 → 期间起身接水10秒: 老化期内回归, ID保持, 会话不中断
 → 晚上问AI"人均在座多久?" → Text2SQL查seat_sessions → "2小时15分"
 → 有人挡镜头: 三信号连续8帧 → 告警条"疑似遮挡", 移开自动恢复
```

### 5.2 用户认证流程

```
注册: 用户名+口令 → 校验唯一性 → PBKDF2(盐+150k迭代)哈希入库
登录: 校验哈希 → 生成 token = base64(user|exp) + HMAC签名 → 前端存 sessionStorage
请求: Authorization: Bearer token → 服务端 HMAC 验签+过期检查(不查库)
管理操作: 再校验 role=admin, 否则 403
```

### 5.3 历史规律计算流程

```
/api/trends?days=7
 → SQL: 按 DATE(ts)×HOUR(ts) 分组求平均占用率(单教室或全馆)
 → 组装 7×24 热力矩阵(无数据为 null)
 → 按 星期×小时 再聚合 → 空座率排序 → 黄金Top3 + 高峰Top3
 → 前端: 热力图 + 日均值柱 + 推荐卡片渲染
```

### 5.4 空座提醒流程

```
登录门户 → 开启提醒(浏览器授权) → 每15秒拉 /api/overview
 → 只看收藏的教室 → free = seats - occupied
 → prev<3 且 free≥3 且 超过5分钟冷却 → 弹 Notification
```

## 六、面试关键点

### 6.1 30 秒开场话术

> "我做了一个智能自习室监测系统。核心难点是俯拍视角下人脸不可见、人脸检测失效，所以我基于 CrowdHuman 数据集自训了 YOLOv8s 人头检测模型，mAP50 0.842。架构上采用边缘计算——检测在教室本机跑，只传数字不传画面，规避带宽和隐私问题。后端 FastAPI + MySQL，前端大屏 + 双角色管理门户，AI 问答用本地 Ollama 做 Text2SQL，全部 Docker 一键部署。"

### 6.2 技术亮点（按被追问概率排序）

**① 训练 768、推理 1280（+5.3 mAP 零成本）**
- 显存只够 768 训练，但推理分辨率可以独立提高——小目标在高分辨率下更清楚
- 体现对"训练/推理解耦"的理解，这是纯调参调不出来的认知

**② Text2SQL + 自愈重试（70% → 95%）**
- 小模型一次生成 SQL 成功率只有 ~70%，把 MySQL 报错原文回喂模型重新生成，一次重试拉到 ~95%
- 用工程手段弥补模型能力，而不是盲目换大模型（后来 7b→1.5b 也是同理：提示词内嵌正确 SQL 示例后小模型也够用，响应从几十秒降到 1.7s）
- 追问"为什么不用 RAG"：结构化时序数据 SQL 精确，语义检索只能给模糊结果

**③ 分级置信度阈值**
- 远景小头置信度天然低（0.2），近处大头高（0.8），统一阈值必挂
- 小框 0.15 / 大框 0.35——"小目标漏检是阈值问题，不是模型问题"

**④ 自研 IOU 跟踪器（NumPy 零依赖）**
- min_hits=3 过滤单帧误检、max_age=12 抗短暂漏检（起身接水不断会话）
- 追问"为什么不用 ByteTrack"：场景静态（坐着为主），杀鸡不用牛刀——技术选型有取舍意识

**⑤ 边缘计算架构**
- 2~4Mbps 视频流 vs 30 秒一次几十字节数字；人脸画面不出本机
- 隐私 + 带宽 + 成本三胜

**⑥ 零模型异常守卫**
- 遮挡 = 亮度↓ + 拉普拉斯方差↓ + 人数=0 三信号与；移动 = 帧差分
- 能讲清楚"为什么三条件同时满足"（夜晚教室暗但纹理仍在，避免误报）

**⑦ 认证安全设计**
- PBKDF2 150k 迭代 + HMAC 无状态 Token；Text2SQL 安全校验（只放行 SELECT + 黑名单 + 强制 LIMIT）
- "删掉 records 表"实测被拦截——有演示故事

**⑧ 数据治理细节**
- occupied 入库前封顶 min(检测数, 座位数)，保证空位永不为负
- 真实踩坑：曾因 AI 裸查 SQL 与统计口径不一致——修复方式是"脏数据不落库"而不是查询时打补丁

### 6.3 可以主动讲的踩坑故事

1. **AdamW 振荡不收敛**：训练早期 loss 下不去，换 SGD 立刻稳定——优化器与学习率要配对
2. **座位坐标映射失败**：早期做过"头框中心落在哪个座位区域"的一对一映射，俯拍遮挡下抖动严重，最终改成"人数=跟踪数，空位=座位−人数"——**把不确定的问题换成确定的问题**
3. **小模型 SQL 幻觉**：1.5b 会编造不存在的 `rooms.occupied_count` 列，靠提示词明确"rooms 表没有任何人数列"+ 内嵌正确 SQL 示例解决
4. **门户 NaN bug**：接口返回 `{summary:{...}}` 嵌套结构，前端取顶层字段拿到 undefined，数字滚动动画算出 NaN——前端取数要跟接口结构对齐

### 6.4 系统设计类追问预案

| 可能的问题 | 回答要点 |
|---|---|
| 如何扩展到 100 间教室？ | 边缘架构天然水平扩展（每教室一个 agent）；服务端无状态可多副本；MySQL 按教室分区/分表 |
| 数据量大了怎么办？ | records 是 5 秒一条的时序数据，可做冷热分层（7 天热数据 + 聚合归档） |
| 为什么不用 Redis/Kafka？ | 当前规模关系型 + 轮询足够；引入中间件是过度设计，但能说清楚何时该引入 |
| AI 问答怎么防注入？ | 只放行 SELECT、黑名单 DDL/DML、强制 LIMIT、错误信息回喂只影响重试 |
| 预约/签到为什么不做？ | 明确产品边界：监测系统的核心是"看得准"，身份绑定需要硬件投入（人脸库/扫码），是演进方向 |

### 6.5 一句话总结

这个项目的面试价值不在"用了很多技术"，而在**每一步都有可量化结果和踩坑过程**：模型有 mAP 数字、AI 有成功率提升、架构有带宽对比、安全有实测拦截——所有决策都能回答"为什么这么做、不这么做会怎样"。
