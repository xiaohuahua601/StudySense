## 一、项目介绍

### 1.1 一句话介绍

**基于自训 YOLOv8s 人头检测模型的智能自习室监测系统**——边缘端实时统计每间教室的人数、空座与在座时长，监测摄像头异常，并用本地大模型提供自然语言数据问答（Text2SQL），形成"监测 → 展示 → 分析 → 推荐"的完整闭环。

### 1.2 背景与痛点

| 痛点 | 本系统的解法 |
|---|---|
| 自习室/图书馆高峰期"找座难"，学生逐间跑 | 大屏/门户实时查看每间教室空座，AI 推荐最优选择 |
| 俯拍视角下学生只见头顶后脑，**人脸检测完全失效** | 改用人头检测（CrowdHuman 数据集自训模型，mAP50=0.842） |
| 管理员不知道哪间教室利用率低、什么时段最挤 | 7天×24h 占用率热力图 + 黄金/高峰时段分析 |
| 视频回传服务器带宽大、隐私风险高 | **边缘计算**：检测在教室本机跑，只传数字不传画面 |
| 通用大模型问答对私有数据无能为力 | 本地 Ollama + Text2SQL，数据不出内网 |

### 1.3 用户与角色

| 角色 | 能力 |
|---|---|
| **访客** | 登录页查看全馆实时统计（教室数/座位数/当前空座） |
| **普通用户** | 占用总览、教室收藏、教室详情（座位示意+24h趋势）、历史规律（热力图/黄金时段）、**座位预测（未来数小时空位预估）**、空座提醒、AI 问答 |
| **管理员** | 教室管理（增删改/级联清数据）、用户管理（新增/升降权/重置密码/删除）、个人中心；**无历史规律与座位预测入口**（面向学生的决策功能） |
| **运营大屏** | 挂墙展示：全局 KPI、实时人流曲线、占用率仪表盘、排行、分时热度 |

### 1.4 核心指标

| 指标 | 数值 |
|---|---|
| 人头检测 mAP50 | **0.842**（CrowdHuman val，4370 图 / 97,285 头框） |
| 单帧推理耗时 | 11.9ms @960 / 152ms @1280（RTX 5070 Laptop，DirectML） |
| 端到端数据延迟 | ≤ 5 秒（上报周期 + 前端轮询） |
| AI 问答 SQL 成功率 | 一次 ~70% → 自愈重试后 ~95% |
| AI 热响应 | ~1.7 秒（qwen2.5:1.5b） |
| 部署方式 | `docker compose up` 一键拉起 4 容器 |

### 1.5 指标名词解释（IoU → mAP 完整链条）

上表的两个检测指标，按"一个检测结果怎么变成一个分数"的链条拆开理解：

**① IoU（Intersection over Union，交并比）**：预测框与真实标注框的重叠程度，`IoU = 交集面积 ÷ 并集面积`，取值 0~1，=1 表示完全重合。

**② IoU 阈值**：判定"检对/检错"的及格线。预测框与某真实框 IoU ≥ 阈值、类别正确、且该真实框未被其他预测抢占 → **TP（检对）**；多检的框是 FP（误检），没被检到的真实框是 FN（漏检）。阈值 0.5（宽松，考"找没找到"）对应 mAP50；0.75~0.95（严格，考"框得贴不贴"）是 mAP50-95 的组成部分。

**③ Precision / Recall**：P = 检出的里面有多少是对的（查准）；R = 该检的里面检出了多少（查全）。

**④ AP（Average Precision，平均精度）**：把置信度阈值从高到低滑动，每个阈值算一组 (P, R)，画出 P-R 曲线，**曲线下面积 = AP**——同时惩罚误检和漏检的单类综合精度。

**⑤ mAP（mean AP）**：所有类别 AP 的平均值。本项目是单类检测（人头），mAP 即该类 AP。

**⑥ mAP50 / mAP50-95 的读法**：

| 数值 | 含义 |
|---|---|
| mAP50 = 0.842 | 100 个头约检出 84 个且误检很低（IoU≥0.5 宽松标准）——"找没找到"考得好 |
| mAP50-95 = 0.546 | 框的贴合精度中等——计数场景不需要框贴得多准，知道"这里有个头"即可 |

**面试话术**：*"IoU 是预测框和真实框的交并比，IoU 阈值是把重叠程度切成对/错的判定线；mAP50 是 IoU 阈值 0.5 下各类别 P-R 曲线下面积的平均，mAP50-95 是 10 个 IoU 档位的平均、更严格地衡量定位精度。我的场景是计数，主看 mAP50。"*

## 二、训练模型数据来源

### 2.1 数据集：CrowdHuman（旷视开源）

| 项 | 值 |
|---|---|
| 规模 | 15,000 训练图 + 4,370 验证图 |
| 场景 | 街景/校园远景人群，多为**俯拍/远距** |
| 标注 | 全身框(fbox) + 头框(hbox) + 可见框(vbox) |
| 头框数量 | 训练集 331,991 个，平均每图 22 个 |
| 关键特性 | 包含**背对镜头**的人——正是俯拍自习室的核心场景 |

**为什么不用人脸数据集（WIDER FACE 等）**：项目早期先训过人脸模型（mAP50=0.99，非常好），但真实自习室顶置摄像头俯拍下学生只有头顶和后脑勺，人脸检测直接失效。这是本项目立项的出发点：**换检测目标（头），而不是换模型**。

### 2.2 数据转换与清洗（convert_crowdhuman.py）

**涉及工具**：自写 Python 脚本（标准库 json/pathlib/argparse + OpenCV 做抽样可视化校验）。

**执行方式**：

```bash
python convert_crowdhuman.py                # 转换 train + val 全量
python convert_crowdhuman.py --split train # 只转训练集
python convert_crowdhuman.py --visualize 10 # 随机抽 10 张画框可视化, 人眼核对
```

脚本逐行读 odgt JSON（自带 JPEG 头解析函数直接读宽高，不解码整图提速），CrowdHuman 原始 odgt 格式（每行一个 JSON）转 YOLO txt 格式（`class cx cy w h` 归一化）。转换不是简单换坐标，关键在**按官方规则过滤脏标注**：

| 过滤项 | 数量(train) | 原因 |
|---|---|---|
| mask 区域内的框 | 85,809 | 被遮挡超阈值，头框质量差 |
| ignore 标记的框 | 20,178 | 官方明确忽略（画面边缘裁切等） |
| 无效框（宽高≤0） | 814 | 坐标越界 |

**质量校验**（抽样 500 图 / 11,420 个头框）：
- 头框中心落在对应全身框内：99.9%
- 头框位于全身框上 40% 区域：96.5%
- 头框平均宽高比 0.86（接近方形，符合头部形状）
- 头宽/全身宽 ≈ 0.38（符合人体比例）

### 2.3 训练配方（WSL + RTX 5070 Laptop 8GB）

**涉及工具**：Ultralytics 框架的 `yolo` CLI（命令行驱动训练，不需要写训练代码）；WSL2 Ubuntu 提供 Linux 训练环境（Windows 下 GPU 直通给 WSL）。

**执行方式**——一条命令启动训练：

```bash
yolo detect train model=yolov8s.pt data=crowdhuman/data.yaml \
  imgsz=768 batch=8 epochs=100 \
  optimizer=SGD lr0=0.01 cos_lr=True patience=30 workers=4
```

参数逐个说明：`model=yolov8s.pt` 从 COCO 预训练权重开始微调（不是从零训练）；`data=data.yaml` 指向 2.2 转换好的数据集清单；`imgsz=768` 输入分辨率；`patience=30` 是早停——验证指标连续 30 个 epoch 无提升自动停止。

- **SGD 而非 AdamW**：实测 AdamW + lr0=0.01 在此任务损失振荡不收敛（真实踩坑），SGD 稳定
- **imgsz=768 / batch=8**：8GB 显存上限（960 会 OOM）
- **patience=30**：第 81 epoch 早停
- 训练档结果：val mAP50 = 0.789

### 2.4 关键技巧：训练 768、推理 1280

**先解释 768 / 960 / 1280 是什么**：它们是模型的**输入分辨率（input size）**——图像进网络前被 letterbox 等比缩放成的正方形边长（像素）。1920×1080 原图进 1280 模型时，会先缩放补边成 1280×1280 再推理。三个数字是同一权重在不同档位下的推理尺寸：768=训练档（显存上限）、960=速度折中档、1280=部署精度档。

**核心认知：训练与推理分辨率可以解耦**——同一权重在不同输入尺寸下推理，小目标在更大输入下保留更多像素细节，因此提高推理分辨率可以零训练成本提升小目标召回。同一权重导出多版 ONNX：

| 推理分辨率 | mAP50 | mAP50-95 | 单帧耗时 |
|---|---|---|---|
| 768（训练档） | 0.789 | 0.494 | 2.3ms |
| 960 | 0.819 | 0.524 | 11.9ms |
| **1280（部署用）** | **0.842** | **0.546** | 152.5ms |

**零额外训练成本，mAP50 +5.3 个点**。自习室帧率要求不高，选 1280 版精度优先。

**ONNX 是什么（面试专业表述）**：ONNX（Open Neural Network Exchange，开放神经网络交换格式）是一套跨框架的模型交换标准。面试话术：*"训练在 PyTorch/Ultralytics 里完成，权重导出为 ONNX 计算图格式，部署侧用 onnxruntime 独立推理引擎加载——训练框架与推理引擎完全解耦，生产环境不依赖训练那套庞大的 Python 栈，运行时只需轻量推理库；ONNX 计算图还能享受算子融合等图优化。"* Windows 下配 onnxruntime-directml 可免装 CUDA 全家桶直接走 GPU。

### 2.5 分级置信度阈值

统一阈值的矛盾：远景小头置信度天然低（~0.2），近处大头高（~0.8）。阈值高则漏小头，低则大框误检泛滥。解法：

```python
# 小框（宽<32px）用低阈值 0.15，大框用高阈值 0.35
threshold = np.where(pred_w * ratio < 32, 0.15, 0.35)
```

## 三、技术栈

| 层 | 技术 | 选型理由 |
|---|---|---|
| 检测模型 | YOLOv8s → ONNX | 单类检测够用；s 版精度/速度平衡 |
| 推理引擎 | onnxruntime-directml | Windows 免装 CUDA 全家桶，DirectML 走 GPU |
| 目标跟踪 | 纯 NumPy 自研 IOU 跟踪器 | 场景静态（坐着为主），ByteTrack 属过度设计 |
| 后端 | FastAPI + PyMySQL | 异步、自动 Swagger、轻量 |
| 认证 | PBKDF2 + HMAC 签名 Token | 无 JWT 依赖、无状态、7 天有效 |
| 数据库 | MySQL 8.0 | 时序快照 + 会话 + 用户，关系型足够 |
| 大屏 | 单文件 HTML + ECharts | 零构建、挂任意屏幕 |
| 管理门户 | Jinja2 SSR 多页应用（FastAPI 同源渲染） | 服务端权限判定 + HttpOnly Cookie + CSRF；替代了 Streamlit 与前端 SPA |
| LLM | Ollama + qwen2.5:1.5b（可切 7b） | 本地运行数据不出内网；1.5b 热响应 1.7s |
| 部署 | Docker Compose（4 服务） | api（含门户 SSR）/ mysql / ollama / dashboard（大屏独立）一键拉起 |

## 四、项目结构与文件作用

> 逐文件说明"这个文件是干嘛的、为什么存在"。理解了这一章，就掌握了整个项目的物理形态；配合第五章的实现细节，即可完整还原系统。

### 4.1 根目录：5 个核心 Python 模块

| 文件 | 角色 | 关键内容 |
|---|---|---|
| `server.py` | **后端中枢（单文件 ~46KB）** | 全部 REST API；启动时自动建库建表/旧表加列迁移；Text2SQL 完整链路（提示词→安全校验→执行→自愈重试→组织回答）；用户认证（PBKDF2 口令哈希 + HMAC 签名 Token）；Jinja2 SSR 门户路由与权限拦截；安全中间件（CSP/CSRF 校验/登录防爆破/CORS 白名单） |
| `edge_agent.py` | **边缘采集端（教室电脑）** | 取流（摄像头 0/视频文件/单图）→ 检测 → 跟踪 → 异常守卫 → 每 interval 秒 `POST /api/report`（只传数字）；视频播完/Ctrl+C 时 `flush_remaining_sessions()` 把在场的人也归档，数据不丢 |
| `head_detector.py` | **人头检测器** | letterbox 等比缩放 → ONNX（onnxruntime-directml 走 GPU）推理 → 分级置信度阈值过滤 → NMS → 坐标映射回原图；默认加载 `models/head_detect_1280.onnx` |
| `tracker.py` | **多目标跟踪器** | 纯 NumPy 实现 IOU+质心跟踪：轨迹预测→匹配→确认（min_hits=3 过滤误检）→老化（max_age=12 抗漏检）→离场会话归档 |
| `camera_guard.py` | **摄像头异常守卫** | 零额外模型：遮挡 = 亮度骤降 + 拉普拉斯方差趋零 + 人数为 0 三信号同时成立；移动 = 相邻帧差分超阈值；60 秒告警冷却防刷屏 |

**为什么后端是单文件**：内部项目优先"一个文件看懂全貌"，省去多模块跳转成本；46KB 仍在可维护规模内（有清晰的分区注释）。这是有意识的取舍，不是偷懒。

## 五、功能具体实现方法

> 本章按统一结构展开每个功能：**实现步骤 → 每个步骤用了什么工具 → 工具的作用 → 工具是怎么执行的**。执行方式分三类标注：**命令行**（终端敲命令）、**Python API**（import 后调用函数/类）、**HTTP 调用**（客户端发请求）。所有代码片段均摘自仓库真实文件，可按文件名对照阅读。

### 5.1 人头检测（head_detector.py）

**功能**：输入一帧 BGR 画面，输出 `[([x1,y1,x2,y2], score), ...]` 人头框列表。整条链路 6 步，前 2 步是一次性离线操作，后 4 步每帧执行。

**步骤 ① 训练模型**（一次性，详见第二章）

| 项 | 说明 |
|---|---|
| 工具 | Ultralytics `yolo` CLI |
| 工具作用 | 提供 YOLOv8 训练全流程（数据加载/增强/反向传播/验证/早停），无需手写训练代码 |
| 执行方式 | **命令行**：`yolo detect train model=yolov8s.pt data=crowdhuman/data.yaml imgsz=768 batch=8 epochs=100 optimizer=SGD lr0=0.01 cos_lr=True patience=30 workers=4`，产出 `best.pt` 权重 |

**步骤 ② 导出 ONNX**（一次性）

| 项 | 说明 |
|---|---|
| 工具 | Ultralytics `yolo export` |
| 工具作用 | 把 PyTorch 权重（best.pt）转成 ONNX 计算图文件，部署侧从此不再依赖 PyTorch |
| 执行方式 | **命令行**：`yolo export model=best.pt format=onnx imgsz=1280`，产出 `models/head_detect_1280.onnx` |

**步骤 ③ 加载推理引擎**（进程启动时执行一次）

| 项 | 说明 |
|---|---|
| 工具 | onnxruntime-directml（`import onnxruntime as ort`） |
| 工具作用 | 轻量推理引擎；DirectML 后端让 Windows 免装 CUDA 全家桶直接走 GPU |
| 执行方式 | **Python API**（`HeadDetector.__init__`） |

```python
self.session = ort.InferenceSession(
    model_path, providers=["DmlExecutionProvider", "CPUExecutionProvider"])
```

providers 列表是**优先级顺序**：GPU 优先、CPU 兜底，GPU 不可用时自动降级，代码零改动。

**步骤 ④ 预处理 letterbox**（每帧）

| 项 | 说明 |
|---|---|
| 工具 | OpenCV + NumPy |
| 工具作用 | 把任意尺寸原图等比缩放补边成 1280×1280，再做色彩/数值/维度变换，拼成模型要的 4 维张量 |
| 执行方式 | **Python API**（`_preprocess`，代码顺序即执行顺序） |

```python
resized = cv2.resize(img, (nw, nh))                      # ① 等比缩放
padded = cv2.copyMakeBorder(resized, t, b, l, r,
             cv2.BORDER_CONSTANT, value=(114, 114, 114))  # ② 补灰边成正方形
rgb   = cv2.cvtColor(img, cv2.COLOR_BGR2RGB)             # ③ BGR→RGB
blob  = padded.astype(np.float32) / 255.0                # ④ 归一化到 0~1
blob  = blob.transpose(2, 0, 1)                          # ⑤ HWC→CHW
blob  = np.expand_dims(blob, 0)                          # ⑥ 加 batch 维
```

为什么 letterbox 不直接 resize：直接拉伸会把头压扁变形，与训练分布不符掉点。

**步骤 ⑤ ONNX 推理**（每帧）

| 项 | 说明 |
|---|---|
| 工具 | onnxruntime `session.run` |
| 工具作用 | 执行计算图前向传播 |
| 执行方式 | **Python API**：`output = self.session.run(None, {self.input_name: blob})[0]`，输出 8400×5——8400 个候选框，每个 (cx, cy, w, h, score) |

**步骤 ⑥ 后处理**（每帧，三个子步骤）

```python
# 6a. 分级阈值过滤（工具：NumPy np.where 向量化，一次算完所有框的阈值）
thresh = np.where(pred[:, 3] * ratio < 80, 0.15, 0.35)
#     原图上框高 <80px 的小头用低阈值 0.15，大框用 0.35

# 6b. 坐标映射回原图（工具：NumPy 广播运算）
#     letterbox 的逆变换: (模型坐标 - pad) / ratio，随后 np.clip 裁到画面边界
boxes[:, 0] = (candidates[:, 0] - candidates[:, 2] / 2 - pad_w) / ratio

# 6c. NMS 去重（工具：NumPy argsort + 广播，自实现 _nms，不调第三方库）
order = scores.argsort()[::-1]   # 按置信度降序，贪心保留
#     与已保留框 IoU > 0.45 的低分框丢弃——同一个头不会出两个框
```

**工具选型关键点（面试可讲）**：
- **为什么不直接用 Ultralytics 推理**：Ultralytics 推理要拖着 PyTorch 整套训练栈（数 GB 依赖）；导出 ONNX 后部署侧只需 onnxruntime 一个轻量包，且计算图可做算子融合优化。训练框架与推理引擎彻底解耦。
- **providers 参数**：声明 DML（GPU）优先、CPU 兜底——GPU 不可用时自动降级，代码零改动。

### 5.2 多目标跟踪（tracker.py）

**功能**：把逐帧检测串成"同一个人"的轨迹，解决"逐帧数人头会抖动"（同一个人这帧检到下帧漏了）。**整个文件零第三方依赖，唯一工具是 NumPy**——IoU 矩阵用广播一次算完（检测框×轨迹框的外积），不写双重循环。

**执行入口**：**Python API**——每帧调用一次 `tracker.update(detections)`（由 edge_agent 主循环驱动），内部 5 步依序执行：

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① IoU 矩阵 | NumPy 广播 | N 条轨迹 × M 个检测框的两两 IoU 一次算完 | `iou_matrix()`：`np.maximum(a[:,None,:2], b[None,:,:2])` 外积式广播得 N×M 矩阵 |
| ② 贪心匹配 | NumPy `argsort` + `unravel_index` | 按分数从高到低依次配对；IoU>0.25 才算同一目标，IoU 不够但质心距离 ≤1.2×框宽的兜底（头小幅移动时 IoU 可能低） | 展平排序索引逐对认领，`tracks[ti].update(det_boxes[di])` |
| ③ 轨迹确认 | 自研状态机（min_hits=3） | 连续命中 ≥3 帧才计入人数——单帧误检（椅背/海报）活不过 3 帧 | `if t.hits >= self.min_hits: t.confirmed = True`，同时记 `first_seen` 时间戳 |
| ④ 轨迹老化 | 自研计数器（max_age=12） | 连续失配 >12 帧才判离场——低头/遮挡短暂漏检不会误判离开 | 未匹配的轨迹每帧 `t.predict()` 即 `age += 1`，超龄销毁 |
| ⑤ 会话归档 | 自研 | 离场轨迹 → `{track_id, start, end}` 会话记录，"人均在座时长"的数据源 | `pop_finished_sessions()` 增量取走随上报发出；`flush_remaining_sessions()` 收尾强制归档在场者 |

**产出**：当前人数 = 返回的已确认轨迹数；参数均在实际自习视频上调优。

### 5.3 摄像头异常守卫（camera_guard.py）

**功能**：零额外模型，检测遮挡/移动两类摄像头异常。**工具全部来自 OpenCV 三个经典函数**。

**执行入口**：**Python API**——每帧调用一次 `guard.update(frame, people_count)`，返回告警 dict 或 None。内部 5 步：

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① 缩图 | `cv2.resize` | 160×90 缩小，统计量计算只要几毫秒 | `gray_small = cv2.resize(gray, (160, 90))` |
| ② 亮度统计 | `ndarray.mean()` | 整帧平均亮度——遮挡时骤降 | `brightness = float(gray_small.mean())` |
| ③ 清晰度统计 | `cv2.Laplacian` + `.var()` | 拉普拉斯边缘响应方差 = 纹理丰富度——镜头被糊/挡时趋零 | `cv2.Laplacian(gray_small, cv2.CV_64F).var()` |
| ④ 帧差分 | `cv2.absdiff` | 相邻帧逐像素差——摄像头被挪动时变化像素占比超阈值 | `ratio = float((diff > 25).sum()) / diff.size` |
| ⑤ 判定与防抖 | 自研状态机 | 三信号与 + 连续帧确认 + 60 秒告警冷却 + 恢复通知（防刷屏） | 计数器连续 N 帧超阈值才触发（见下表） |

| 异常 | 判定信号（同时成立） | 确认条件 |
|---|---|---|
| 遮挡 | 亮度 <35 **且** 拉普拉斯方差 <80 **且** 检测人数 = 0 | 连续 8 帧 |
| 移动 | 帧差分变化像素占比 >25% | 连续 4 帧 |

为什么三条件同时满足才算遮挡：夜晚教室暗但纹理仍在——只看亮度会误报。

### 5.4 边缘上报（edge_agent.py）

**功能**：教室电脑上的常驻进程，串起"取流 → 检测 → 跟踪 → 守卫 → 周期上报"整条链路。

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① 解析参数 | argparse（Python 标准库） | 命令行指定视频源/上报间隔/教室标识 | **命令行**：`python edge_agent.py --camera-id room_201 --source media/test_room.mp4 --interval 30` |
| ② 取流 | OpenCV `cv2.VideoCapture` | 统一三态取流：摄像头(0)/视频文件/单图 | **Python API**：`cap.read()` 每帧一次；摄像头模式额外 `cap.set(CAP_PROP_FRAME_WIDTH, 1280)` 设分辨率 |
| ③ 检测+跟踪 | `from head_detector import HeadDetector` / `from tracker import IOUTracker` | 每帧人头检测 → 更新轨迹 → 得到稳定人数 | **Python API**（主循环内）：`detections = detector.detect(frame)` → `tracked = tracker.update(detections)` |
| ④ 异常守卫 | `from camera_guard import CameraGuard` | 每帧检查遮挡/移动，有告警即上报 | **Python API**：`alert = guard.update(frame, len(tracked))`，非 None 时 `report_alert()` |

**上报 payload 结构**（`build_payload()` 组装）：

### 5.5 用户认证（server.py）

**功能**：注册/登录/无状态 Token 验证/防爆破。**零第三方认证库，全部 Python 标准库 + FastAPI 自带机制**。

**步骤 ① 密码哈希入库**（注册/改密码/管理员重置时执行）

| 项 | 说明 |
|---|---|
| 工具 | `hashlib.pbkdf2_hmac` + `secrets.token_hex`（标准库） |
| 工具作用 | PBKDF2-SHA256 12 万次迭代拉伸——单次哈希耗时故意拉长，暴力破解成本极高；随机盐防彩虹表 |
| 执行方式 | **Python API** |

```python
salt = secrets.token_hex(16)          # 每用户独立随机盐
h = hashlib.pbkdf2_hmac("sha256", password.encode(),
                        salt.encode(), 120_000).hex()
```

**步骤 ② 签发 Token**（登录成功时执行）

| 项 | 说明 |
|---|---|
| 工具 | `hmac.new` + `base64.urlsafe_b64encode` + `json.dumps`（标准库） |
| 工具作用 | 类 JWT 自研结构 `base64url(payload).hex(HMAC签名)`——服务端不存 session，验证不查库 |
| 执行方式 | **Python API**（`_make_token`） |

```python
payload = _b64(json.dumps({"uid": ..., "username": ...,
                            "role": ..., "exp": now + 7天}))
sig = hmac.new(TOKEN_SECRET.encode(), payload.encode(),
               hashlib.sha256).hexdigest()
return payload + "." + sig
```

**步骤 ③ 请求验证**（每个受保护接口执行）

| 项 | 说明 |
|---|---|
| 工具 | FastAPI `Depends` 依赖注入 + `hmac.compare_digest` |
| 工具作用 | 从 HttpOnly Cookie 或 `Authorization: Bearer` 双通道取 token → HMAC 验签 → 过期检查；`compare_digest` 恒定时间比较防时序攻击 |
| 执行方式 | **Python API**：声明即生效 |

```python
def current_user(request: Request,
                 authorization: str = Header(None)) -> dict: ...

@app.get("/api/auth/me")
def me(user: dict = Depends(current_user)): ...   # 自动先执行验证
```

**步骤 ④ 管理接口角色校验**：`require_admin = Depends` 再包一层，非 admin 返回 403。

**步骤 ⑤ 防爆破**：登录连续失败 5 次锁账号 15 分钟（内存计数器实现）。

### 5.10 座位预测（/api/forecast + portal/forecast.html，普通用户专属）

**功能**：预估未来 1~12 小时各教室的空位数，帮学生"现在出发、到了有座"。**可解释的统计基线模型**——不是黑盒 ML，预测依据和置信度直接展示给用户。

**权限设计**：接口层管理员直接 403（"空位预测面向普通用户"）；页面层 `/portal/forecast` 对管理员 302 重定向回总览——与管理员无"历史规律"入口同一设计哲学（学生决策功能不给管理端）。

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① 取未来时段 | Python `datetime` + `timedelta` | 把"未来 N 小时"展开成逐小时预测目标（当前时刻取整到小时） | **Python API**：`targets = [now + timedelta(hours=i) for i in range(1, hours+1)]`，hours 由查询参数传入并 clamp 到 1~12 |
| ② 第一层预测（同星期同小时） | MySQL 聚合 SQL | 过去 **84 天（12 周）**里相同星期、相同小时的日均人数——"下周三 15 点"就用历史所有周三 15 点的数据，最贴近目标场景 | **Python API**（`cursor.execute` 参数化查询）：子查询按 `camera_id × DATE(ts)` 先求日均、再对日均求平均，`WHERE WEEKDAY(ts)=%s AND HOUR(ts)=%s` |
| ③ 第二层兜底（同小时放宽日期） | 同上 | 数据刚积累时"同星期同小时"样本可能为 0，放宽为任意日期的同小时日均值——**宁可用粗数据，不伪造** | 同结构 SQL 去掉 WEEKDAY 条件；教室级二选一：第一层有样本用第一层，否则用第二层，`basis` 字段标明用了哪层 |
| ④ 结果加工 | Python 纯函数 | 预测人数 clamp 到 [0, 总座位]（空位永不为负）；`predicted_free = 总座位 - 预测人数`；样本量分级置信度（≥4 高 / ≥2 中 / 其余低） | `max(0, min(total_seats, round(...)))`；结果按 `predicted_free` 降序排——第一个就是推荐教室 |
| ⑤ 前端渲染 | forecast.html + `api()` 封装 | 逐小时卡片墙：推荐教室⭐置顶、每教室显示"预计 N 空位"；页首展示预测方法说明（可解释性落地） | **HTTP 调用**：`api("/api/forecast?hours=3")` → 按 slot 渲染卡片 |

**为什么是统计基线而不是 ML 模型**：自习室人流有强周周期（课表驱动），"12 周同星期同小时日均"已能捕捉；数据量不足以训模型时统计基线反而更稳；且预测依据（同星期同小时/样本数/置信度）能完整讲给用户听——**可解释性本身就是功能**。

### 5.11 AI 问答（意图路由 + Text2SQL + 本地 Ollama）

选 **Text2SQL 而非 RAG**：数据是结构化时序数字，SQL 精确（"15点平均29.2人"），语义检索只能给模糊相似结果。

**架构分两层**：高频问题走规则层（不经 LLM，零幻觉零延迟），长尾问题走 LLM 兜底。

**第一层：意图路由（高频问题，7 类）**

| 项 | 说明 |
|---|---|
| 工具 | `re` 标准库（正则匹配）+ 预写 SQL 模板 + Python 字符串渲染 |
| 工具作用 | "人最多/人最少/最空/空位最多/空位最少/某教室几人/某教室空位/什么时间去最空" 关键词命中即返回固定 SQL——答案由 Python 确定性渲染，**无论什么模型什么温度都不会答错** |
| 执行方式 | **Python API**（`/api/ask` 接口内先调）：`_route_intent(db, question, camera_id)` 正则匹配 → 选模板 → 教室名单里对号入座 → 返回 (kind, sql)；执行后 `_render_intent_answer(kind, rows)` 拼成中文句子 |

**第二层：LLM Text2SQL（长尾问题兜底，五步链路）**

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① 生成 SQL | Ollama REST API（`urllib.request` 调用） | qwen2.5 按 schema 提示词生成 SQL | **HTTP 调用**：POST `{OLLAMA_URL}/api/generate`，payload 带 `options.temperature=0.1`（低温保确定性） |
| ② 安全校验 | 自研 `_safe_sql`（纯 Python 字符串检查） | 只放行 SELECT/WITH 开头；黑名单拦 insert/update/delete/drop 等 12 个关键字；剥 markdown 围栏 | 前缀 + 关键字双检查，不合法返回 None 直接拒绝 |
| ③ 执行 | PyMySQL `cursor.execute` | 跑 SQL 拿结果 | 强制 LIMIT 50 防大结果集 |
| ④ 自愈重试 | 错误回喂机制 | MySQL 报错原文 + 全库 Schema 拼进新提示词让模型改——成功率 70%→95% | 最多 2 次，仍失败则返回兜底话术 |
| ⑤ 组织回答 | Ollama 二次调用 | 查询结果 + 原问题 → 中文自然语言回答 | 同 ①；前端不展示 SQL，仅后端调试字段保留 |

实测："删掉 records 表"被步骤 ② 拦截——有演示故事。模型选择：qwen2.5:1.5b 热响应 ~1.7s（7b 需几十秒）；小模型幻觉靠**规则前置 + 强化 schema 提示 + 自愈重试**工程手段弥补。

### 5.12 部署与容器编排（Docker Compose 四服务）

**功能**：`docker compose up -d` 一键拉起 api(8000)/mysql(3307)/ollama(11435)/dashboard(8080)。

| 步骤 | 工具 | 工具作用 | 执行方式 |
|---|---|---|---|
| ① 构建后端镜像 | Dockerfile（api） | python:3.10-slim + pip 装依赖（清华源）+ COPY server.py/web/templates | **命令行**：`docker build`（compose up 时自动触发）；CMD 启动 uvicorn |

## 六、功能实现流程

### 6.1 端到端数据流（一次完整旅程）

```
教室摄像头
 → edge_agent: 检测(8个头) + 跟踪(8条轨迹) + 守卫
 → 新人入画, 连续3帧确认, ID=7, 人数8→9
 → 30秒到: POST /api/report {camera_id, head_count:9}
 → MySQL records 落库(occupied 封顶 min(9, 45) ≤ 座位数)
 → 大屏5秒内轮询到: 卡片闪橙光"▲+1", 曲线末端跳到9
 → 2小时后离开: 12帧未匹配 → 会话归档{track_id:7, 14:00→16:00}
 → 期间起身接水10秒: 老化期内回归, ID保持, 会话不中断
 → 晚上问AI"人均在座多久?" → Text2SQL查seat_sessions → "2小时15分"
 → 有人挡镜头: 三信号连续8帧 → 告警条"疑似遮挡", 移开自动恢复
```

### 6.2 用户认证流程

```
注册: 用户名+口令 → 校验唯一性 → PBKDF2(盐+12万迭代)哈希入库
登录: 校验哈希 → 生成 token = base64(user|exp) + HMAC签名
     → Set-Cookie(HttpOnly + SameSite=Strict) 写入浏览器
     → 同时响应体返回 token(编程调用走 Authorization: Bearer, 双通道)
浏览器请求: Cookie 自动携带 → 服务端 HMAC 验签+过期检查(不查库)
写操作: 额外校验 X-Requested-With 头(CSRF 防护)
管理操作: 再校验 role=admin, 否则 403
```

### 6.3 历史规律计算流程

```
/api/trends?days=7
 → SQL: 按 DATE(ts)×HOUR(ts) 分组求平均占用率(单教室或全馆)
 → 组装 7×24 热力矩阵(无数据为 null)
 → 按 星期×小时 再聚合 → 按空座率排序
 → 黄金Top3 = 空座率最高的3个时段
 → 高峰Top3 = 剩余时段中空座率最低的3个(与黄金互斥, 杜绝自相矛盾)
 → 前端: 热力图 + 日均值柱 + 推荐卡片渲染(前端再兜底过滤一次)
```

### 6.4 空座提醒流程

```
登录门户 → 开启提醒(浏览器授权) → 每15秒拉 /api/overview
 → 只看收藏的教室 → free = seats - occupied
 → prev<3 且 free≥3 且 超过5分钟冷却 → 弹 Notification
```

### 6.5 座位预测流程

```
普通用户打开 /portal/forecast (管理员302回总览)
 → GET /api/forecast?hours=3 (管理员403)
 → 逐个未来小时: 过去12周同星期同小时日均 → 样本不足回退同小时(任意日期)
 → 预测人数 clamp [0, 座位数] → predicted_free = 座位 - 预测人数
 → 按空位降序 + 置信度(样本数)分级 → 前端卡片墙(推荐教室⭐置顶)
```

## 七、面试关键点

### 7.1 30 秒开场话术

> "我做了一个智能自习室监测系统。核心难点是俯拍视角下人脸不可见、人脸检测失效，所以我基于 CrowdHuman 数据集自训了 YOLOv8s 人头检测模型，mAP50 0.842。架构上采用边缘计算——检测在教室本机跑，只传数字不传画面，规避带宽和隐私问题。后端 FastAPI + MySQL，前端大屏 + 双角色管理门户，AI 问答用本地 Ollama 做 Text2SQL，全部 Docker 一键部署。"

### 7.2 技术亮点（按被追问概率排序）

**① 训练 768、推理 1280（+5.3 mAP 零成本）**
- 显存只够 768 训练，但推理分辨率可以独立提高——小目标在高分辨率下更清楚
- 体现对"训练/推理解耦"的理解，这是纯调参调不出来的认知

**② Text2SQL + 自愈重试（70% → 95%）**
- 小模型一次生成 SQL 成功率只有 ~70%，把 MySQL 报错原文回喂模型重新生成，一次重试拉到 ~95%
- 用工程手段弥补模型能力，而不是盲目换大模型（后来 7b→1.5b 也是同理：提示词内嵌正确 SQL 示例后小模型也够用，响应从几十秒降到 1.7s）
- 追问"为什么不用 RAG"：结构化时序数据 SQL 精确，语义检索只能给模糊结果

**③ 分级置信度阈值**
- 远景小头置信度天然低（0.2），近处大头高（0.8），统一阈值必挂
- 小框 0.15 / 大框 0.35——"小目标漏检是阈值问题，不是模型问题"

**④ 自研 IOU 跟踪器（NumPy 零依赖）**
- min_hits=3 过滤单帧误检、max_age=12 抗短暂漏检（起身接水不断会话）
- 追问"为什么不用 ByteTrack"：场景静态（坐着为主），杀鸡不用牛刀——技术选型有取舍意识

**⑤ 边缘计算架构**
- 2~4Mbps 视频流 vs 30 秒一次几十字节数字；人脸画面不出本机
- 隐私 + 带宽 + 成本三胜

**⑥ 零模型异常守卫**
- 遮挡 = 亮度↓ + 拉普拉斯方差↓ + 人数=0 三信号与；移动 = 帧差分
- 能讲清楚"为什么三条件同时满足"（夜晚教室暗但纹理仍在，避免误报）

**⑦ 认证安全设计**
- PBKDF2 12 万迭代 + HMAC 无状态 Token；Text2SQL 安全校验（只放行 SELECT + 黑名单 + 强制 LIMIT）
- "删掉 records 表"实测被拦截——有演示故事

**⑧ 数据治理细节**
- occupied 入库前封顶 min(检测数, 座位数)，保证空位永不为负
- 真实踩坑：曾因 AI 裸查 SQL 与统计口径不一致——修复方式是"脏数据不落库"而不是查询时打补丁

**⑨ 为什么自训模型而不用现成的（选型论证，主动讲体现判断力）**

现成方案在本场景逐一失效：

| 现成方案 | 实际问题 |
|---|---|
| COCO 预训练 YOLO（80 类） | 没有"人头"类别，检的是全身 person；俯拍下人被桌椅挡住大半，召回率低 |
| 人脸检测模型 | 项目早期实测 mAP50=0.99，但俯拍视角学生只有头顶后脑勺，**直接失效**——立项依据 |
| crowd counting 密度计数模型 | 只输出密度图/总数，拿不到单人头框，跟踪与在座时长会话统计做不了 |

需要的"单类人头框检测 + 俯拍域"在模型库里是空白，自训才成立。自训的收益：

1. **域适配是硬收益**：俯拍 + 背对镜头 + 密集遮挡不在通用模型的训练分布里；CrowdHuman 恰含背对镜头样本——数据集选型本身就是一次域匹配决策
2. **单类 = 更小更快**：只训一类可放心用 s 版，没有 79 个无用类别的推理开销
3. **推理链路可控**：同一权重可导出 768/960/1280 三档 ONNX 按需切换精度/速度——"训练 768、推理 1280"只有自训权重做得到
4. **问题自己修**：上线后发现误检（如椅背），标几百张微调即可；用别人模型只能等作者更新——工程主导权
5. **可被追问三层不穿帮**：为什么换检测目标（人脸失效）→ 为什么选 CrowdHuman（背对镜头）→ 为什么训 768 推 1280（显存限制 + 推理解耦），每层都有实测数据

**边界（主动讲加分）**：如果场景是普通视角人体检测、通用分类——直接用现成模型才是正确决策。选型判断标准是"现成的能否满足精度和输出形态"；本场景不满足，自训才不是练手而是必须。

### 7.3 可以主动讲的踩坑故事

1. **AdamW 振荡不收敛**：训练早期 loss 下不去，换 SGD 立刻稳定——优化器与学习率要配对
2. **座位坐标映射失败**：早期做过"头框中心落在哪个座位区域"的一对一映射，俯拍遮挡下抖动严重，最终改成"人数=跟踪数，空位=座位−人数"——**把不确定的问题换成确定的问题**
3. **小模型 SQL 幻觉**：1.5b 会编造不存在的 `rooms.occupied_count` 列，靠提示词明确"rooms 表没有任何人数列"+ 内嵌正确 SQL 示例解决
4. **门户 NaN bug**：接口返回 `{summary:{...}}` 嵌套结构，前端取顶层字段拿到 undefined，数字滚动动画算出 NaN——前端取数要跟接口结构对齐

### 7.4 系统设计类追问预案

| 可能的问题 | 回答要点 |
|---|---|
| 如何扩展到 100 间教室？ | 边缘架构天然水平扩展（每教室一个 agent）；服务端无状态可多副本；MySQL 按教室分区/分表 |
| 数据量大了怎么办？ | records 是 5 秒一条的时序数据，可做冷热分层（7 天热数据 + 聚合归档） |
| 为什么不用 Redis/Kafka？ | 当前规模关系型 + 轮询足够；引入中间件是过度设计，但能说清楚何时该引入 |
| AI 问答怎么防注入？ | 只放行 SELECT、黑名单 DDL/DML、强制 LIMIT、错误信息回喂只影响重试 |
| 为什么不用现成的检测模型？ | 俯拍 + 背对镜头场景现成模型逐一失效（人脸模型实测失败即立项依据）；"单类人头框 + 俯拍域"是空白；完整论证见 7.2 ⑨ |
| 预约/签到为什么不做？ | 明确产品边界：监测系统的核心是"看得准"，身份绑定需要硬件投入（人脸库/扫码），是演进方向 |

### 7.5 一句话总结

这个项目的面试价值不在"用了很多技术"，而在**每一步都有可量化结果和踩坑过程**：模型有 mAP 数字、AI 有成功率提升、架构有带宽对比、安全有实测拦截——所有决策都能回答"为什么这么做、不这么做会怎样"。
